# 3D 国际象棋 AI 升级方案

> 状态:**阶段一 ~ 四已实施完成**(纯 JS + Worker + 难度下拉 + 状态栏搜索信息),
> 阶段五(WASM)按 §4.4 的决策规则暂不启动。实测结果见 §九。
> 目标:把当前的「一层贪心」换成可调节强度的真搜索引擎,并针对 WASM 路线给出明确取舍依据。

---

## 一、现状诊断

`js/apps/chess3d/index.js` 第 344 行起的 `aiMove()`:

```js
for (每个我能动的格子)
  for (每个合法着法)
    score = (吃到的子 ? VAL[t] * 10 : 0) + Math.random() * 3   // ← 随机数直接参与决策
    if (送到被子攻击的格子) score += 2
  取 score 最高的一步
```

三个致命缺陷:

1. **只看一层**:对手下一步反吃完全看不见。经典的「送后」「叉子」陷阱一个都躲不掉。
2. **没有静态搜索**:搜索深度到达上限时如果正处在交换子力的中途(比如刚吃掉一个兵、自己的后正被攻击),评估会把这个「未结算」的局面当成最终局面,得出完全错误的结论 —— 这就是地平线效应。
3. **随机数扰动**:`Math.random() * 3` 的量级与 1 个兵的价值同数量级,导致 AI 在不同步之间的判断标准不一致,表现像一个发挥极度不稳定的新手。

此外 `applyMove()` 每次都 `cloneB()` 深拷贝整个棋盘,在搜索中每节点一次全盘拷贝,是纯粹的性能浪费。

**棋规引擎本身是对的**(我上次验证过 perft 级别的基本走子、易位、吃过路兵逻辑),所以这次是「换引擎内部的搜索与评估」,**不是重写规则**。

## 二、目标

多档可调强度,用户能在 UI 上直接选。每档给固定的「思考时间预算」,由引擎自己决定能搜多深。

| 档位 | 时间预算 | 预期深度 | 说明 |
|---|---|---|---|
| 初级 | ~50ms,深度上限 2 | 1–2 | 保留少量随机,给新手留出赢面 |
| 中级 | 400ms | 5–6 | 明显强于休闲玩家,能抓住简单战术 |
| 高级 | 1.5s | 6–8 | 默认推荐档 |
| 大师 | 4s | 8–10 | 慢,但能吃掉中级 AI 送的所有子 |

> 深度数字是**预估**:取决于走法排序质量和 NPS(每秒节点数),阶段一实测后校准。

## 三、方案主线:纯 JS 引擎 + Worker(推荐)

### 3.1 文件拆分

现在文件是一个人 400 行的单体, Three.js 渲染和棋规搅在一起。按职责切开:

```
js/apps/chess3d/
  index.js     UI + Three.js 渲染 + 交互(瘦身后的现状)
  rules.js     棋规:走法生成、make/unmake、Zobrist 哈希
  ai.js        搜索(PVS/迭代加深)+ 评估函数
  worker.js    薄壳:收 { history, budget, level } → 回 { move, depth, nodes, ms, score }
  board.js     开局库(可选,阶段四)
tools/chess-engine-test.mjs   perft + 战术局面测试
```

**硬性约束**:`rules.js` 与 `ai.js` 不得 import three、不得碰 DOM。
这样带来两个好处:① Worker 可以直接 `import` 它们;② `tools/*.mjs` 能在 **Node 里直接跑**,不用开浏览器就能做 perft 和战术测试 —— 这是整个方案里性价比最高的一条。

同样的架空预留:所有 UI 只通过一个统一的 `engineApi` 调用引擎,将来换 WASM 实现只替换这一层。

### 3.2 内部表示:make/unmake + Zobrist

> **修订(Rev.2)**:原方案写的是「保留现有 `board[r][c] = {t, c}` 对象语义以方便回归对比」。**这是个错误的取舍**,见 §3.7 的说明 —— 对象数组在搜索热路径上会成为 JS 版最大的性能瓶颈。改为下面的平坦表示,旧实现只作为测试里的答案参考(orcle)留存。

- **棋盘**:`Int8Array(64)` mailbox,棋子编码成小整数(`(color<<3)|type`,0 表示空格),不用对象。
- **棋子列表**:每色一个 `Int8Array(16)` 存格号 + 格子→下标的反向表。遍历己方棋子时不必扫满 64 格。
- **走法**:单个 int32 打包(起点 / 终点 / 吃子 / 升变 / 易位标志位),每层预分配 `Int32Array(256)` 缓冲区。**搜索全程零对象分配** —— 这是 JS 引擎特有的收益:没有分配就没有 GC,没有 GC 就不会随机掉帧。
- **make/unmake**:原地修改 + undo 栈(扁平 typed array),不再 `cloneB`。undo 记录:被吃子、原 castle 权、原 ep、是否易位/升变。
- **Zobrist 哈希**:每格 × 12 种棋子一个随机数(mulberry32 生成,和黑白棋 `index.js` 第 64 行的写法同源),外加走子权、8 个 ep 文件、16 种 castle 权。增量 XOR 更新。
  - 用途一:**置换表**。2^20 槽,存 key/深度/score/flag(EXACT | LOWER | UPPER)/最佳着法。
  - 用途二:**重复局面检测**。用历史 key 判和,避免 AI 在优势局面里来回兜圈被判和。

### 3.3 搜索

沿用黑白棋已验证的骨架(PVS 负极大 + 迭代加深 + `await yieldUI()`),补充象棋专属的部分:

- **α-β / PVS**:主变全窗口搜,其余用零窗口探测,失败再重搜。
- **静态搜索(quiescence)**:叶子节点的分数不可信,必须沿「吃子 + 升变」继续展开直到局面安静。这是**修复地平线效应唯一有效的手段**,也是这次升级里性价比最高的一项。会加 δ 剪枝和简单的 SEE 过滤掉明显亏本的吃子。
- **走法排序**:TT 最佳着法 → 吃子按 MVV-LVA(用最小的子吃最大的子)→ killer moves → history 启发式。排序质量通常能换来 1–2 层实际深度,比优化评估函数更值。
- **将军延伸**:被将军时 depth + 1(限总延伸次数),避免最典型的那类失误 —— 在被连续追杀时,搜索边界正好卡在杀棋前一步。
- **终局处理**:将死返回 `-(MATE - ply)`,逼和返回 0。带 ply 的目的是让 AI 在多个杀法中**选最短的那个**,而不是把对手遛一整局。

### 3.4 评估函数

从「吃掉什么」升级为「局面好不好」:

- **子力**:`p=100 n=320 b=330 r=500 q=900`
- **棋子位置表 PST**:兵推进加分、马占中心避边线、车占开放线和第七横线、象怕被自己的兵堵住、王中局躲角落残局出来干活。**中局表与残局表按子力余量线性插值**。
- **王安全**:王周围己方兵的数量( Shield 缺口 / 开放线大幅扣分)、敌方重子对王区的攻击格计数。
- **兵结构**:叠兵、孤立兵、落后兵各给少量惩罚。
- **双象**:残局 +30 左右。

> PST 数值我会从社区通用的一组取值出发,再用实际对局自测微调 —— 不宣称「调优过」直到真的跑出数据。

### 3.5 不卡 UI:Web Worker

三种做法里推荐 **Worker**:

| 方案 | 评价 |
|---|---|
| Worker | 推荐。UI 侧改造成本很低:引擎是纯 JS 模块,Worker 直接 import 即可。`postMessage` 传走法序列(FEN 或 UCI 串),不传棋盘对象。唯一代价是异步化需要小心处理「用户在 AI 思考时点了新对局/关窗口」的竞争条件 —— 用请求序号丢弃过期结果即可。 |
| 主线程分段 `await yieldUI()` | 黑白棋现有做法,改动最小,但预算只能给到 300–600ms 否则每帧卡顿能感觉到。 |
| Worker + 降级 | 两份代码路径,调试成本翻倍,不建议优先做。 |

Worker 还带来一个额外好处:**将来换 WASM 时天然就在正确的位置**,UI 线程完全不受影响。

### 3.6 UI 联动

- 工具栏「人机:开」按钮 → 升级为难度下拉/循环按钮:初级 / 中级 / 高级 / 大师。
- 状态栏右侧(`Three.js r160` 旁边)显示实时搜索信息:`深度 6 · 128kN · 0.8s · +0.7`。
- 思考中时有明确提示,并支持「换边视角/拖拽」继续操作。
- **兼容保障**:`window.__chess` 的 `click/turn/board` 三个钩子保持签名不变,`tools/e2e.mjs` 里的 T33.2 用例不受影响;另外追加 `stats()` 里的 AI 信息。

### 3.7 剪枝增强:同预算下真正拉开差距的那几项(Rev.2 增补)

原方案只列了教科书主干(PVS + TT + 排序 + 静态搜索),**漏掉了现代引擎提升深度最主要的几招**。在同一个 CPU 预算下,这几项带来的收益远大于调评估参数:

| 技术 | 干的事 | 相对收益 | 实现成本 | 坑 |
|---|---|---|---|---|
| **空着剪枝 Null-move pruning** | 轮到自己走但存在 β 以上的静态分时,直接「不走这步」搜浅一层;剪不掉才正常搜 | **最高**,通常 +1~2 层 | 低(约 30 行) | 残局只有王兵时必须关掉(zugzwang 会误判) |
| **迟着裁减 LMR** | 排序靠后的安静着法自动减一层,引发 α 提升再补搜 | 高,+1 层以上 | 低 | 参数敏感(pv/被将军/吃子/升变都要例外) |
| **Aspiration window** | 迭代加深时用上一层的分数 ±50 开局窗口,而非全窗口 | 中,省下大量重搜 | 极低 | 窗口失败要放宽重搜 |
| **静态布局 pruning(futility / reverse futility)** | 明显追不上 α 的着法直接剪掉,不再搜索 | 中 | 低 | 别在有将军可能的局面启用;要与 *mate distance* 保护一起用 |
| **历史/续着排序 history & continuation history** | 取代简单的 killer:按着法在兄弟节点中的历史表现排序 | 中到高 | 中 | 表很大,要用 `Int32Array` 并做局面项归一化,否则 GC/内存咬回来 |
| **静态搜索内 SEE 过滤 + Δ 剪枝** | 进 qsearch 前用 SEE 判断这个交换是否明显亏本 | 中 | 中 | SEE 写错会直接漏战术,必须用 perft 级别的单测守住 |
| **延伸:将军 / 吃回** | 将军时 +1 层,吃回最后一层通常 +小量 | 中(主要是消除边界假窗口) | 低 | 延伸总量必须封顶,否则深度爆炸 |

**收益排序总结**:「怎么搜索」比「怎么评估」更值钱 —— 在我们这种 5–8 层的浅搜索里,战术能力主导棋力,所以精力和预算应该优先砸在搜索侧的改进上;评估函数的边际收益要到 10 层以上才明显上升。

反过来,以下几件在这个预算下**不划算**(写清楚以免后面又想做):

- **JS 版 NNUE**:NNUE 的强度来自「每个 Eval 用几十万次 int8 乘加换来的精度」,这在 C++ 里靠 AVX/SIMD 摊薄到几微秒;JS 是标量执行,同样的推断会把 NPS 打下去一个数量级,**大概率是净亏损**。
- **MCTS(AlphaZero 那条路)**:没有策略/价值网络就没有 prior,MCTS 退化成随机模拟,同等 CPU 预算下远弱于 α-β。这条路要 GPU,与「3D 网页小游戏」的场景无关。
- **MTD(f)**:依赖极好的置换表和稳定的评估,在 PST 评估 + 大写表命中率不足时收益不稳定,与 PVS + aspiration 基本持平。收益不够退路的复杂度和隐患。
- **終局残子库**:文件体积动测评几十 MB,违反项目资源约束。

## 四、WASM 专项评估

你提了 WASM,这部分我认真算过账,**结论是不建议作为第一阶段**,理由如下。

### 4.1 前置成本(实测本机状态)

```
cargo / rustc / rustup      未安装
wasm-pack / emscripten      未安装
clang / wat2wasm            未安装
```

也就是说走 Rust-to-WASM 路线需要先装:rustup + Rust 工具链 + `wasm32-unknown-unknown` target + `wasm-bindgen`,以及 `wasm-opt`(否则产物偏大)。这是一笔几百 MB 到上 GB 的安装量,而且是**每个贡献者都要重复付出的成本**。

### 4.2 收益

WASM 版引擎可以用真正的 u64 位棋盘 + 完全无 GC 的数据结构。相对优化过的 JS:

| 指标 | 纯 JS(带 make/unmake) | Rust → WASM |
|---|---|---|
| 预期 NPS | 约 5万 – 20万 | 约 30万 – 100万 |
| 同等时间预算下的额外深度 | — | **大约 +1 ~ 2 层** |
| 确定性 | 依赖 JIT,有 deopt 风险 | 稳定 |

> 数字是基于位棋盘 vs 对象数组的经验估计,**未经本机实测**。要确证只能两边都写一遍跑 bench,那本身就是一个不小的工作量。

### 4.3 成本

1. **二进制入仓库**:`.wasm` 文件 100–300KB,committed binary blob,review 时看不见内容变化。
2. **构建链路变长**:`npm run build` 不再够用,变成 `cargo build --release && wasm-bindgen && npm run build`(需要写进 npm script 和 CI)。README 现在对外强调的是「无后端、产物丢到任意静态服务器即可运行」,引入 wasm 后产物会多出一个二进制文件(仍是静态文件),这条会被削弱。
3. **调试体验倒退**:浏览器断点打不进 Rust 源码(需要配 dwarf + 特定插件),回溯信息远不如 JS 直观。perft 调试会痛苦很多。
4. **贡献门槛**:以后任何人想改象形 AI 的一条评估规则,都要先装 Rust。

### 4.4 结论与决策规则

**建议路径:先做阶段一(纯 JS + Worker),把接口层抽干净。WASM 作为阶段二的可选项,按需启动。**

什么时候才值得上 WASM —— 用阶段一的**实测数据**判定,而不是凭感觉:

- 若高级档(1.5s 预算)在 NPS ≥ 15万 的机器上仍**达不到稳定 6 层**,且主要瓶颈是搜索速度而非评估质量 → 再谈 WASM。
- 若已经能稳定 6–8 层,WASM 换来的 1–2 层对「3D 休闲对弈」这个场景几乎无感 → 不值得为一个 Chat UI 里的小游戏引入 Rust 工具链。

如果最终决定上 WASM,推荐形态是:**Rust + wasm-bindgen 写位棋盘引擎 → 放进现有 Worker** → 通过一个统一的 `engineApi`(与 JS 版签名完全一致)切换。由于阶段一已经把这层接口隔离好了,替换成本会很低,这才是本方案真正为 WASM 留下的东西。

### 4.5 现成的开源方案:chessy 的调查结论(Rev.3)

仓库 `den-run-ai/chessy`(MIT)。**核实过的事实**(2026-09-17):

| 项目 | 实测结果 |
|---|---|
| Star / Watch | **1 / 0**;创建于 2026-07-15,最后推送 2026-09-16;29 个开放 issue |
| 形态 | 一个完整的离线 PWA(自带 2D 棋盘 + 复盘/教学/IndexedDB),不是引擎库 |
| WASM 产物 | `assets/chessy-ai-fast.wasm`,**仅 37 KB** |
| Rust 源码 | 有,在 `experiments/wasm/src/`(`engine.rs` 37KB / `search.rs` 48KB / `eval.rs` 15KB / `lib.rs` 8KB,约 2400 行) |
| 集成接口 | 裸指针 ABI-v2(`history_input_ptr` / `pv_ptr` / `abi_move`),需自己写 JS 侧线性内存读写器 |
| 评估 | PeSTO 风格 tapered eval(`VALUES_MG/EG` + 相位插值)+ mobility / 叠兵孤立兵 / 王盾 |
| 评级说明 | README 自称 1500/1700/1900/2100/2300+ 是**自我标定的暂定目标**,非 FIDE/Chess.com/Lichess 认证 |

**它实际实现了什么**(读 `search.rs` 确认):Zobrist 置换表、`quiesce_node` 静态搜索、history/killer 排序(`record_quiet_cutoff`)、MVV-LVA、节点预算闸门、`check_node_repetition` 搜索路径重复检测、 insufficient material 处理。

**它没有实现的**:`Null`(空着剪枝)= 0 处、`reduction`/LMR = 0 处、`futility`/`razor` = 0 处、`aspiration` = 0 处、`prob_cut` = 0 处。

**结论:不引入依赖,但把它当参考实现。** 理由:

1. **它的强度天花板 ≈ 本方案 §3.7 减去那四项剪枝**。我们自己写就是「它有的全都有 + 四项改良」,引入它反而是用一个更低、且无法再调优的天花板,换掉我们本来就打算实现的那四项剪枝。37KB 的产物也说明这是个中等规模 HCE 引擎,不是什么碾压级东西。
2. **它是整机 App,不是库** —— 要用的话得把 wasm 和它的 `wasm-engine.js` loader 剥出来适配裸 ABI,还得我们自己解 `window.__chess` 那套 Board↔ABI 转换。省下的代码量没有看上去那么多。
3. **上游风险**:1 star / 0 watch / 29 issue / 两个月新 / 仓库里 20KB 的 `CLAUDE.md` 和 `AGENTS.md`(典型的 agent 驱动开发痕迹)。冻结一个 third-party 二进制,等于把 our engine 的 bus factor 交出去。

**要从它那里拿走的东西(这几点确实比我原方案好,已并入 Rev.3)**:

| 采纳项 | 为什么比我原来的做法好 |
|---|---|
| **用「节点上限」而不是「墙上时间」做难度预算**(`check_budget`,10k/36k/230k/1.44M + 5s 兜底上限) | 时间预算在不同设备上棋力会漂移;节点预算是**设备无关、可复现**的,还能让测试断言"这个局面在 N 节点内必须找到正解",AI 的回归测试从此是确定性的。原 §2 的 ms 预算表改为「节点上限为主 + 时间兜底」。 |
| **搜索路径内的重复局面也要记 0 分**(不只对局历史) | 让 AI 在赢棋时主动避开重复、输棋时会奔向长将。这是 `
root_completed_threefold` + `check_node_repetition` 两个函数做的事,我原方案只写到"对局历史判和",漏了 search-path。 |
| **低难度档用「在最优解 N 分以内随机挑」代替「给评分加随机噪声」**(`shuffle_root`) | 原方案给 score 加 `Math.random()` 会让 AI 在同一局面表现前后不一致;在 root 挑相近着法才是正统做法,既弱得可控又不离谱。 |
| **直接复用它的 perft 标准局面(Kiwipete 等)与 insufficient-material 规则表** | 直接复用它的测试局面做 our fixture,比我手写局面覆盖更全。 |

初始局面 20 / 400 / 8902 / 197281;Kiwipete 48 / 2039 / 97862 / 4085603;局面3 14 / 191 / 2812 / 43238;局面4 6 / 264 / 9467 / 422333。

### 4.6 现成的开源方案二:Wasabi(mhonert/chess)—— 参考价值高,许可证是硬门槛(Rev.4)

**核实过的事实**(2026-09-17):

| 项目 | 实测结果 |
|---|---|
| 形态 | AssemblyScript(TS 语法 → WASM)写的国际象棋引擎 + React 前端 |
| Star / 活跃度 | **108 star**;2019-11 建仓;**最后推送 2024-04-23**(约两年半未动);最近 release v1.5.0 在 **2020-07** |
| 许可证 | **GPL-3.0-or-later**(我们项目是 MIT) |
| 预编译产物 | 仓库内无 wasm;release 附 `wasabi-v1.5.0-engine.wasm` **370 KB**(2020 年) |
| 构建方式 | `npm i -D assemblyscript` + `asc`(**纯 npm 工具链,不要 Rust**) |
| 评估 | 参数用 Zurichess 的 725000 局面做过回归调参 —— 这是我明确说过自己做不到的事 |

**它的技术清单**(读 `assembly/engine.ts`,893 行实证):

| 空着剪枝 `// Null move pruning`、迟着裁减 `// Reduce search depth for late moves`、futility pruning、静态搜索 quiescence、SEE(7 处)、历史启发式(23 处)、Zobrist 置换表、PV | aspiration window、razoring、Δ 剪枝、将军延伸 |

**结论**:

1. **许可证是硬门槛,不是技术取舍**。GPL-3.0 与我们的 MIT 项目不兼容:把它的源码或编译产物并入并分发,整体作品需要以 GPL-3.0 提供源码。要开这条路,得先把整个 WebOS 项目改成 GPL-3.0 —— 这是你的产权决定,不是我能替你做的。
2. **可以读,不可以抄**。GPL 不禁止阅读和借鉴思路,但逐行翻译到近乎一致的实现有「派生作品」风险。正确用法是拿它当**行为规格**:验证技术清单、核对边界条件。
3. **更正我在 §4.1 的一个论断**。我说过「上 WASM 要装 Rust 工具链」——那只针对 **Rust**。Wasabi 证明 AssemblyScript 是纯 npm 工具链,不需要任何 SDK。修正后写进§5 阶段五:将来真要上 WASM,**优先评估 AssemblyScript 而不是 Rust**(TS 语法、无需额外 SDK、构建能并入 `npm run build`)。
4. **它反过来确认了 §3.7 是对的**。一个 108 star、有真实用户、评估参数调过参的引擎,用的正是「空着剪枝 + LMR + futility + 静态搜索 + SEE + 历史启发式」这套。这套是这类引擎的**共识底线**,我们不该低于这个配置。

## 七、体积预算:引擎产物 ≤ 35 KB(Rev.5)

### 7.1 先说清楚 35 KB 约束落在谁头上

实测当前构建产物(`dist/assets/`):

| 产物 | 原始 | gzip |
|---|---|---|
| **`app-chess3d-*.js`** | **454 KB** | **116 KB** ← 几乎全是 three.js |
| `app-reversi-*.js`(黑白棋引擎+UI 全套) | 12.9 KB | 5.3 KB |
| `core-*.js` | 77 KB | 27.9 KB |
| `index-*.js` | 30.5 KB | 11.9 KB |

**结论:35 KB 不可能落在整个 `app-chess3d` 分包上** —— 它现在已经是 116 KB gzip,其中约 110 KB 是 three.js。除非放弃 3D,否则那条约束无解。

所以约束的合理解释是:**AI 引擎部分单独成块(放 Worker,自然独立成一个 chunk),这个 chunk 的压缩后体积 ≤ 35 KB**。这也是唯一可执行的定义,下文按这个口径评估。

### 7.2 实测得出的单价

用项目里已有的真实产物反推(而不是拍脑袋):

- `app-reversi-*.js`:775 行源码(含 UI)→ 12.9 KB minified / 5.3 KB gzip
  ⇒ **minified 约 17 B/行,gzip 约 7 B/行**(这是 Vite + terser 真实产物,不是粗略估算)
- PST 数据(12 棋子 × 64 格 × 中局/残局 = 3072 个值)实测:数组字面量 5.2 KB 原始 / 2.2 KB gzip;紧凑字符串编码 3.2 KB / 2.1 KB gzip(**gzip 后几乎无差别**,所以按可读性选数组字面量即可)

### 7.3 预算表

| 模块 | 预计行数 | minified | gzip |
|---|---|---|---|
| `rules.js` 走法生成 + make/unmake + Zobrist | ~450 | 7.7 KB | 3.2 KB |
| `ai.js` 搜索(PVS/空着/LMR/futility)+ TT + 排序 + 静态搜索 + SEE + 评估 | ~430 | 7.3 KB | 3.0 KB |
| PST 数据表 | (数据) | 5.2 KB | 2.2 KB |
| `worker.js` + engineApi + 难度预设 | ~80 | 1.4 KB | 0.6 KB |
| **合计** | **~960** | **约 21.6 KB** | **约 9.0 KB** |

对 35 KB 的余量:

- **按 gzip(传输体积)算:9.0 KB / 35 KB,余量 26 KB。** 宽裕。
- **按 minified 原始字节算:21.6 KB / 35 KB,余量 13 KB。** 也够,但不宽裕。

误差说明:这是按每行单价外推,真实值可能有 ±30% 偏差。所以 phases 一 / 二 结束后我会**实测一次**,把数字钉死。

### 7.3.1 实测结果(已完成,数字已钉死)

`npm run build` 后由 `tools/check-size.mjs` 直接量 gzip(level 9),不再外推:

| 模块 | 源码行数 | 源码字节 | 备注 |
|---|---|---|---|
| `rules.js` | 483 | 18,425 | 棋规 + make/unmake + Zobrist + replayMoves |
| `ai.js` | 608 | 23,973 | 搜索 + 剪枝 + SEE + 评估(含 PST 表数据) |
| `ai-worker.js` | 41 | 1,543 | 薄壳 |
| **合计(源码)** | **1,132** | **43,941** | — |
| **打包后 chunk** | — | **15,446 raw / 6,179 gzip** | **占 35 KB 预算的 17.2%** |

**比预估(9.0 KB gzip)还低 31%**,原因找到了:预估用的「7 B/行」单价是从黑白棋量的,
而黑白棋源码里中文注释占比远低于本引擎 —— 本引擎 43.9 KB 源码里有大量「为什么这么做/
踩过什么坑」的中文注释,压缩时被整体剥掉,产物只占源码的 35%。**估计这类体积时,
注释密度是比行数更强的自变量。**

> 结论:gzip 口径下余量 29 KB,按 minified 原始字节算余量 19.5 KB。§7.5 的降级顺序**一条都不需要动用**。
> 余量虽大,但不建议为了「把预算用满」而加评估项 —— §3.7 已经论证过,这个深度区间里
> 搜索侧的收益远大于评估侧,而当前 §3.7 列的技术已全部实现。

### 7.4 让约束可执行:加体积门禁

不建议靠自觉。做法:写一个 `tools/check-size.mjs`,在构建后遍历 `dist/assets/`,找到引擎 worker 的那个 chunk,gzip 后超过 35 KB 就非零退出,并挂到 `npm run build` 之后。这样体积是**被断言的**,不是被希望的。

### 7.5 万一超标的降级顺序(按性价比从先砍到后砍)

1. 砍开局库(本来就没计划,Wasabi 那份数据 369 KB,绝对不能要)
2. 砍 SAN / FEN 解析 —— Worker 协议只传走法序列和节点预算,不需要完整记谱
3. PST 改紧凑字符串编码(minified 省 2 KB,gzip 省 0.1 KB)
4. 评估项做减法:先砍 mobility(需要额外遍历),保留子力 / PST / 兵结构 / 王盾
5. 砍 futility / razoring 这类纯加速项(**静态搜索不能砍**,它关系到正确性,不是性能项)

### 7.6 附:three.js 能不能瘦身 / 换库(Rev.6,**已执行 ✅**)

> **执行结果(Rev.7)**:已换用 ogl 1.0.11 并移除 three。`app-chess3d` chunk 从 **454 KB / 116 KB gzip → 80.7 KB / 24.8 KB gzip**(4.7×)。渲染 + 真实阴影 + 点击拾取 + 走子/AI 全部经无头 Chrome 探针验证通过,零控制台错误。
> 过程中修了两个 ogl 阴影特有的坑:① `Shadow` 自建 RenderTarget 默认 LINEAR 过滤,会插值破坏 RGBA 打包的深度 → 换 NEAREST;② 深度通道清屏色会混入场景背景色,导致只接收阴影的棋盘整体误判进阴影 → 阴影 pass 前把清屏色改为白色(深度 1.0)。
> 点击拾取没有用 `Raycast.intersectBounds`(包围球对扁平方格会重叠),改为射线与棋盘平面求交 + 格子坐标换算,更准也更小。

用户追问「three 能否缩减或更换」。全部为**实测数据**,不是估计:

| 方案 | 原始 | gzip | 说明 |
|---|---|---|---|
| three r160 现状 | 460.0 KB | **116.2 KB** | — |
| three **按需引入**(只 import 实际用到的 16 个类) | 460.0 KB | **116.2 KB** | **tree-shaking 完全无效**:`WebGLRenderer` 会把整个渲染器(着色器块/材质/光照)拖进来 |
| **ogl**(按需 11 类:Renderer/Camera/Transform/Box/Sphere/Cylinder/Program/Mesh/Vec3/Color/Geometry) | 50.8 KB | **14.9 KB** | ESM 源码分发,可 tree-shake |
| **ogl** 完整需求集(再加 Plane/Orbit/Raycast/**Shadow**/Mat4) | 73.4 KB | **21.0 KB** | 有真实阴影模块,能力基本对齐 |
| **zdog** | 29 KB | **7 KB** | 伪 3D(Canvas/SVG),**无光照无阴影**,视觉风格完全不同 |
| twgl.js | 388 KB | 73 KB | 太大 |
| regl | 293 KB | 60 KB | 太大 |
| **纯手写 WebGL**(无库) | — | 约 3–5 KB | 需自己写约 400–700 行(相机/网格生成/着色器/拾取) |

**ogl 与 three 的能力对照**(当前 chess3d 用到的东西都有对应):

| three | ogl |
|---|---|
| `Scene` | `Transform`(根节点) |
| `PerspectiveCamera` | `Camera` |
| `WebGLRenderer` | `Renderer` |
| `BoxGeometry` / `CylinderGeometry` / `SphereGeometry` | `Box` / `Cylinder` / `Sphere` |
| `MeshStandardMaterial` + 灯光 | **没有光照系统**,需自写约 20 行 GLSL(一个方向光 + 环境光) |
| `Raycaster` | `Raycast` ✔ |
| 自写的 theta/phi 轨道 | `Orbit` ✔(也可保留我们自己的,省体积) |
| `castShadow` / `shadowMap` | `Shadow` ✔ |

**两个前提事实**:

1. **three 目前已是懒加载** —— 应用通过 `js/apps/index.js` 的动态 `import()` 分发,`app-chess3d-*.js` 是独立 chunk,用户不打开象棋就完全不会加载 three。所以如果 35 KB 约束指的是引擎 chunk,**three 根本不参与**,不用动。
2. **three 只有 chess3d 在用**(全仓库 grep 确认)。换库的影响面就这一个文件,不牵连其他应用。

**结论**:

- 若 35 KB = 引擎 chunk → **不用动 three**,预估 9 KB 已经满足。
- 若 35 KB = 整个 `app-chess3d` chunk → **换 ogl 是唯一现实的选择**:21 KB(或精简到 15 KB)+ 引擎 9 KB + UI 约 5 KB ≈ **29–35 KB gzip**,刚好压线;若要更宽松,可只取 ogl 最小集(14.9 KB)、保留自写轨道数学与假阴影。纯手写 WebGL 能到约 18 KB,但要多写几百行且失去依赖维护。zdog 虽只有 7 KB,但会彻底改变视觉(变扁平卡通风),属于重新设计,不是优化。
- 换库的代价:重写 `index.js` 的渲染段(约 150–250 行)+ 一个 GLSL 着色器,并重新做视觉验证。**好消息是我们已经有 `tools/probe-chess.mjs`**,能自动断言"画面真的渲染出来了、像素多样性达标",验证成本很低。

### 9.4 两个必须记住的实现约定(踩过)

1. **走法有两套编码**:UI ↔ Worker 传输用线格式 `(from<<6)|to`(`replayMoves` 按此解析);
   引擎内部 `mkMove(from,to,flag,cap)` 是 `from` 在**低 6 位**。
2. **升变一律取升后**:`replayMoves` 只还原升后,所以 UI 拿到任何升变都必须先规整成升后
   (`index.js` 的 `normalize()`),否则本地局面与 Worker 重演出的局面会不一致。

另外,Worker 里的搜索是同步跑的,消息只会排队:**要真中断只能 `terminate()` 再新建**
(新对局 / 换档 / 关窗),日常靠请求自增 id 丢弃过期结果即可。
